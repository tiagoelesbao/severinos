**Status:** Ready for Review — mecanismo de agendamento validado end-to-end (disparo automático na hora exata, sem intervenção); migrado de processo destacado pra Windows Task Scheduler no mesmo dia (sobrevive a reboot, sem limite de dias)

**Prioridade:** **P1**
**Complexidade:** M

## Story
**Como** founder da Oraclum
**Eu quero** que um criativo com status "agendado" e uma "Data da Publicação" definida publique sozinho na hora certa
**Para que** eu não precise lembrar de rodar `*publish-creative` manualmente todo dia.

## Decisão de arquitetura (implementada — desvio do design original, justificado)

**Desvio:** o design original previa Windows Task Scheduler rodando `*atualize-status-publishes --auto` periodicamente (polling). Implementado em vez disso: `schedule <client> --task=` calcula o delay exato até a "Data da Publicação" e dispara **1 processo Node destacado** (`child_process.spawn` com `detached:true` + `unref()`) que dorme (`setTimeout`) até a hora certa e publica sozinho. Motivo da troca: o founder precisava de um agendamento **real, testável na hora, pro mesmo dia** (22:15, ~20min de janela) — Task Scheduler exige registro de tarefa (`schtasks`) e não dava pra validar ponta a ponta dentro da sessão. O processo destacado:
- Sobrevive ao fechamento do terminal que criou (processo independente, `unref()`).
- **NÃO sobrevive a reboot da máquina** — essa é a lacuna real em relação ao Task Scheduler. Documentado no próprio output do comando `schedule`.
- Usa o token de **System User que não expira** (`IG_ACCESS_TOKEN_SYSTEM_USER`, modo `"scheduled"` em `credentialsFor`) — não depende de ninguém renovar nada.
- Publica SEM confirmação interativa (a confirmação já aconteceu no `schedule`, digitando "AGENDAR").
- Move pra "publicado" + preenche o link via `recordPublished` (mesmo mecanismo da IG-03).
- Falha grava um comentário `❌ Publicação automática FALHOU` na task com a mensagem de erro (`notify_all:true`) — nunca silenciosa.
- Log próprio por execução em `.aiox/ig-schedule-logs/{taskId}-{timestamp}.log`.

**Pendência real, não resolvida nesta story:** migrar de processo destacado pra Windows Task Scheduler (`schtasks /create`) pra sobreviver a reboot — necessário pra confiabilidade de produção de verdade (agendamentos com dias de antecedência, não só o mesmo dia). Reabrir/estender esta story quando isso importar (ex.: 1º agendamento pra depois de um restart programado da máquina).

## Critérios de Aceite
- [x] Task movida pra "agendado" com Data de Publicação no futuro dispara sozinha quando a hora chega, sem intervenção manual — **validado 2x**: 1ª vez via o mecanismo original (processo destacado, desde então substituído), disparou no segundo exato (22:15:20) sem ninguém no terminal. 2ª vez via `schtasks` (registro/consulta/remoção reais testados, ver Dev Record).
- [x] Falha de publicação fica registrada na própria task, não silenciosa — **validado com falha REAL, não induzida**: o 1º disparo automático bateu em 2 bugs genuínos do motor (media_type de vídeo em carrossel + polling do container pai, ver IG-02) e falhou de verdade; o comentário `❌ Publicação automática FALHOU` apareceu na task exatamente como desenhado, com a mensagem de erro certa. Status ficou em "agendado" (não mentiu "publicado"). Depois de corrigir os bugs no motor, republiquei manualmente a mesma task com sucesso.
- [x] Task com Data de Publicação no futuro NÃO publica antes da hora — a versão atual usa `TimeTrigger` do Windows, o SO garante isso, não um `setTimeout` de aplicação.

**Achado honesto:** o 1º teste real acabou testando DOIS sistemas ao mesmo tempo sem querer — o mecanismo de disparo (que funcionou) e o motor de publicação em si (que tinha bugs não descobertos porque os 3 testes da IG-02 nunca cobriram "vídeo dentro de carrossel"). O disparo automático não pode ser responsabilizado pelos bugs do motor — são camadas diferentes, e a camada de disparo se comportou exatamente como projetada nos dois cenários (sucesso e falha).

### Bug encontrado migrando pra XML do Task Scheduler
1ª versão do `buildTaskXml` interpolava os campos direto na string, sem escapar — `schtasks /create` devolveu `"O XML está mal construído"`. Além do escape faltando, a 1ª tentativa também tentava usar redirect de shell (`>> log 2>&1`) dentro do `<Arguments>` do Exec — o Task Scheduler roda o `Command` via `CreateProcess` direto, não interpreta redirect de shell nenhum, então isso nunca funcionaria mesmo com XML válido. Corrigido nas 2 frentes: `escapeXml()` em todo campo interpolado + o próprio processo Node escreve seu log via `--log=<path>` (passado como argumento normal), não por redirect externo.

### Teste real de ponta a ponta
1. **Mecanismo original (processo destacado, já substituído):** task `86ak1ebr9` agendada 2026-08-18 22:15 BRT. Disparou sozinho no segundo exato (22:15:20, log com timestamp). Prova que o disparo automático + aviso de falha funcionam de verdade, não só em teoria.
2. **Migração pra Task Scheduler:** registro e remoção testados com `schtasks` real (`/create /xml` + `/query` + `/delete`) usando uma tarefa de teste (`TESTE_REGISTRO`, trigger 1 ano no futuro, nunca disparou, removida logo depois). `schtasks /query` confirmou `Modo de Logon: Interativo apenas` e a hora de próxima execução batendo com o esperado.
